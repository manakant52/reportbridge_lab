# WireGuard Web Portal

Этот проект больше не использует Telegram-бота. Сейчас это веб-портал для выдачи WireGuard-конфигов через браузер.

Дополнительная документация:

- `DEPLOY.md` - полная инструкция по развертыванию
- `OPERATIONS.md` - эксплуатация, проверки и типовые проблемы
- `DNS.md` - настройка внутреннего DNS через `dnsmasq` на VPN-хосте

Портал умеет:

- создавать invite-коды
- выдавать конфиг и QR-код
- хранить профили и invite-коды в SQLite
- автоматически добавлять и удалять peer'ов из живого `wg0`
- разделять профили по ролям `red` и `blue`

## Что сейчас реализовано

Текущая схема:

- один сайт
- один интерфейс WireGuard: `wg0`
- две роли доступа:
  - `red`
  - `blue`

Роли отличаются не разными сайтами и не разными ботами, а:

- разными пулами IP
- разной серверной политикой доступа

## Роли

### `red`

- адреса выдаются из подсети `10.10.100.0/24`
- клиентский конфиг получает `AllowedIPs = 0.0.0.0/0`
- DNS для клиентов роли: `10.10.100.1`
- на сервере действует ограничение:
  - доступ в локальные сети разрешен только к `10.10.10.0/24`

Итого:

- `red` выходит в интернет через сервер
- `red` может ходить только в `10.10.10.0/24`
- `red` не может ходить в остальные `10.10.0.0/16`

### `blue`

- адреса выдаются из подсети `10.10.110.0/24`
- клиентский конфиг получает `AllowedIPs = 0.0.0.0/0`
- DNS для клиентов роли: `10.10.110.1`
- на сервере для `blue` разрешены только нужные внутренние сегменты

Итого:

- `blue` выходит в интернет через сервер
- `blue` может ходить в `10.10.10.0/24`
- `blue` может ходить в `10.10.20.0/24`
- `blue` может ходить в `10.10.30.0/24`
- `blue` не может ходить в другие сети из `10.10.0.0/16`

## Почему роли разведены по разным подсетям

Это сделано специально.

Если бы `red` и `blue` сидели в одной и той же VPN-подсети, сервер не смог бы нормально различать их через firewall.

Сейчас это решается правильно:

- `red` = `10.10.100.0/24`
- `blue` = `10.10.110.0/24`

Из-за этого серверу легко применить разные правила firewall и разный DNS для клиентов.

## Как работает выдача

Пользователь:

1. открывает сайт
2. вводит имя
3. вводит invite-код

Портал:

1. проверяет invite
2. определяет роль invite-кода
3. выбирает IP из соответствующего пула
4. генерирует ключи
5. сохраняет peer в БД
6. создает клиентский `.conf`
7. обновляет managed peer block
8. применяет изменения в live `wg0`
9. показывает страницу со скачиванием и QR-кодом

## Admin-панель

Админка находится по пути:

- `/admin`

Через нее можно:

- создавать invite-коды
- выбирать роль invite-кода: `red` или `blue`
- задавать количество активаций
- смотреть список invite-кодов
- смотреть выданные профили
- отзывать профили
- перевыпускать профили

Пароль админки задается через:

- `WEB_ADMIN_PASSWORD`

## Важная правка БД

Раньше был баг:

- `UNIQUE constraint failed: peers.vpn_ip`

Причина:

- старый revoked peer сохранял IP
- новый peer пытался получить тот же IP
- вставка падала на глобальном `UNIQUE`

Что сделано:

- глобальный `UNIQUE` с `vpn_ip` убран
- вместо него создан уникальный индекс только для `status='active'`

Теперь:

- активные профили не конфликтуют по IP
- revoked профили могут оставаться в истории
- IP можно переиспользовать после revoke

## Переменные окружения

Текущее направление конфигурации такое:

```env
DB_PATH=/var/lib/vpn_tg_bot/tg_vpn_bot_project/bot.db
CONFIG_DIR=/var/lib/vpn_tg_bot/tg_vpn_bot_project/configs
WG_INTERFACE=wg0
WG_CONFIG_PATH=/etc/wireguard/wg0.conf
WG_MANAGED_PEERS_PATH=/etc/wireguard/wg0-managed-peers.conf
WG_SERVER_PUBLIC_KEY=SERVER_PUBLIC_KEY_HERE
WG_ENDPOINT=SERVER_PUBLIC_IP:51820
WG_DNS=1.1.1.1
WG_DNS_RED=10.10.100.1
WG_DNS_BLUE=10.10.110.1

WG_ALLOWED_IPS_RED=0.0.0.0/0
WG_ALLOWED_IPS_BLUE=0.0.0.0/0

WG_CLIENT_IP_NETWORK_RED=10.10.100.0/24
WG_CLIENT_IP_START_RED=102
WG_CLIENT_IP_END_RED=220

WG_CLIENT_IP_NETWORK_BLUE=10.10.110.0/24
WG_CLIENT_IP_START_BLUE=102
WG_CLIENT_IP_END_BLUE=220

APPLY_CHANGES=true
DEFAULT_INVITE_USES=10
WEB_HOST=0.0.0.0
WEB_PORT=8080
WEB_TITLE=Портал доступа WireGuard
WEB_ADMIN_PASSWORD=change-me
```

## Что делает `APPLY_CHANGES`

Это переключатель между:

- безопасным режимом
- боевым режимом

### Если `APPLY_CHANGES=false`

Портал:

- пишет peer'ов в БД
- генерирует клиентские конфиги
- обновляет managed peers файл
- не применяет изменения в live `wg0`

Это удобно для тестов и безопасной отладки.

### Если `APPLY_CHANGES=true`

Портал:

1. обновляет блок `# BEGIN TG VPN MANAGED PEERS ... # END TG VPN MANAGED PEERS` в `/etc/wireguard/wg0.conf`
2. применяет изменения в живой интерфейс `wg0`

То есть:

- выдал конфиг -> peer сразу появился в `wg show wg0`
- revoke -> peer сразу исчез из `wg0`
- rotate -> ключи сразу обновились на сервере

## Как сейчас реализован боевой режим

Боевой режим уже включен.

Используется не “тестовый” сценарий, а live-применение.

На сервере сейчас:

- `APPLY_CHANGES=true`
- `net.ipv4.ip_forward=1`
- NAT для VPN-клиентов включен
- `wg0` обновляется автоматически при выдаче и revoke
- внутренний DNS может раздаваться с этого же VPN-хоста через `dnsmasq`

## Варианты запуска

### Вариант 1. Нативный запуск на хосте

Используется:

- `systemd`
- `.venv`
- unit `tg-vpn-bot.service`

Этот вариант проще в отладке и прямолинейнее, потому что приложение работает прямо на хосте.

### Вариант 2. Podman в отдельной директории

Для контейнерного запуска подготовлен отдельный стек.

Он живет отдельно от основного проекта и должен деплоиться в:

- `/opt/web_vpn_podman`

В нем используются:

- `Containerfile`
- `compose.yaml`
- `env/web-vpn.env`
- `systemd/web-vpn-podman.service`

Важно:

- WireGuard все равно остается на хосте
- контейнер работает с `host network`
- контейнеру нужен доступ к `/etc/wireguard`
- контейнеру нужен `NET_ADMIN`

Подробности смотри в `DEPLOY.md`.

## WireGuard и сеть

### Что сейчас настроено на сервере

В `wg0.conf` используются правила:

- включение `ip_forward`
- NAT из VPN-подсетей в `eth0`
- разрешение forwarding для `red` и `blue`
- отдельный `DROP` для `red -> 10.10.10.0/24`

Текущая логика:

- `10.10.100.0/24` -> интернет разрешен, `10.10.10.0/24` запрещен
- `10.10.110.0/24` -> интернет разрешен, локалка разрешена

### Почему интернет у клиента сначала не работал

Проблема была не в ключах.

Handshake работал, а трафик не шел, потому что:

- `net.ipv4.ip_forward` был выключен
- оставались старые restrictive firewall-правила
- не было `MASQUERADE` для выхода через `eth0`

Это уже исправлено.

## Что происходит при создании invite

Теперь invite создается не только с количеством активаций, но и с ролью:

- `red`
- `blue`

Код invite имеет соответствующий префикс:

- `RED-...`
- `BLUE-...`

## Что происходит при выдаче профиля

### `red`

Пример:

- профиль получает IP вроде `10.10.100.102`
- peer добавляется в `wg0`
- сервер режет доступ в `10.10.10.0/24`

### `blue`

Пример:

- профиль получает IP вроде `10.10.110.102`
- peer добавляется в `wg0`
- сервер не режет локалку для этого профиля

## Команды для проверки

Проверка статуса портала:

```bash
systemctl status tg-vpn-bot.service
journalctl -u tg-vpn-bot.service -n 100 --no-pager
```

Проверка WireGuard:

```bash
wg show wg0
```

Проверка firewall:

```bash
iptables -S FORWARD
iptables -t nat -S POSTROUTING
```

Проверка forwarding:

```bash
sysctl net.ipv4.ip_forward
```

## Что важно помнить

Ограничение `red` сделано не только на клиенте, а именно на сервере.

Это принципиально важно.

Если бы ограничение было только через `AllowedIPs` в клиентском конфиге, пользователь мог бы обойти это изменением локального конфига.

Сейчас защита делается правильно:

- клиент получает конфиг
- сервер дополнительно сам режет доступ для `red`

## Текущее назначение проекта

Это self-hosted WireGuard access portal с role-based access policy:

- `red` для ограниченного доступа
- `blue` для свободного доступа по локальной сети

И все это управляется через один сайт и один WireGuard-интерфейс.
